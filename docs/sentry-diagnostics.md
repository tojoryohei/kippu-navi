# エラー診断とWorkerの自動復旧

## Sentryで確認する情報

- `search_error`: 既存のエラー分類、能力、HTTPステータス、再試行・再起動回数。
- `engine_diagnostics`: 元例外、実際に起動したWorker URL、Worker自身のURL、世代、資材取得履歴、最後に到達した初期化段階。API失敗でもこの共通診断contextを使う。
- `engine_diagnostics.attempts`: 自動再起動後も失敗した場合の初回・再試行の診断。
- `engine_recovery`: 復旧後の検索が別のエラーで失敗した場合に、初期化の復旧結果を添付する。
- `api_fallback`: APIからローカル計算へ移った後の失敗で、元のAPI失敗とローカル処理の結果を添付する。
- `browser_diagnostics`: 表示状態、オンライン状態、Worker/WebAssemblyの利用可否、直近のAstro遷移の到達段階。

資材履歴にはURL、処理段階、試行番号、経過時間、取得できたHTTPステータス、タイムアウト、フォールバック元を残す。動的importのHTTPステータスや空のErrorEventの位置情報など、ブラウザから取得できない情報は補完しない。元例外のメッセージは1,000文字、スタックは8,000文字、資材履歴は初期化1回につき32件が上限。

URLのクエリ・フラグメントは保持する。レスポンス本文・ヘッダーを新たに収集せず、APIの既存の`X-Request-ID`による照合は維持する。Sentryの送信経路・fingerprint・既存の除外条件は変更しない。

## 復旧の範囲

`ensureReady()`の再試行可能な初期化失敗だけを対象に、共有Pool単位で一度だけ再起動する。初回・再起動後はそれぞれ最大30秒。同時に待機している画面と能力は期限・再起動予算を共有する。実行中要求があるときは`recoverySuppressed: active_requests`を記録し、再起動しない。画面破棄後も終端通知までは計算要求を実行中として扱う。

再失敗後は自動再起動を繰り返さず、既存の「計算を再試行」で新しいサイクルを開始する。計算要求を自動再送せず、資材・APIの取得リトライ回数と間隔は変えない。古い世代のメッセージとエラーは無視する。

復旧成功のためのSentryイベントは追加しない。検索成功時の復旧状況は既存の`search_completed`の`engine_recovered`・`worker_restart_count`で確認する。APIからローカル計算へ移った検索には`api_fallback_outcome`・`api_error_code`も付く。元の直接捕捉イベントに、後から復旧結果が追記されるわけではない。

## 本番反映後

1. ChromeのSentryで対象リリースの次の実イベントを確認し、元例外・資材URL・処理段階・試行履歴が読めることを確認する。
2. 2W・9のWorker読み込み障害、ZなどのLoad failed、10・1Zの初期化タイムアウトを別々に調べる。資材取得、本文読み取り、WASM生成、グラフ初期化のどこで止まったかを確認する。
3. API障害は既存request IDとサーバーログを照合する。画面遷移・一般例外は遷移段階と元のスタックを照合し、外部注入を推測だけで除外しない。
4. 検索成功イベントの復旧回数と合わせて影響を判断する。診断追加やイベント減少だけで2Wなどを解決済みにしない。
