# PWAの検証と復旧

## 仕様

保存・更新の状態は更新履歴ページの「アプリの状態」だけに表示し、ほかの画面には通知を出さない。追加時のURLの検索条件を復元し、入力の永続保存はしない。
API優先、オフライン・通信失敗・タイムアウト・HTTP 408・429・5xxで全券種の端末内検索に切り替える。HTTP 429はAPIを再試行せず切り替える。
自動検索の表示を変更せず、経路入力検索の既存進捗バーは維持する。

HTML・JS・CSS・画像・Noto Sans JP・WASM・路線データを版単位で保存する。
更新時は同じURL・SHA-256の資材を旧版から新版キャッシュへコピーし、変更・追加・欠損した資材だけを取得する。旧版候補はインストール開始時に一度取得した `kippu-pwa-` キャッシュ（新版自身を除く）に限定する。旧版の読み出し・検証失敗は次の候補またはネットワークへ進むが、新版への保存失敗はインストール失敗とし、旧版を維持する。破損した旧キャッシュは再利用せず、正常なデータを別候補またはネットワークから取得する。
URLが変わった資材は新規取得する。初回・保存領域削除後は全件取得し、更新待機中は旧版と新版の両方を保存する。
登録はstandalone表示のみ。初回のオンライン起動中に準備し、初回保存後の次のナビゲーションからService Workerが制御する。
保存した一式が揃うまで旧版を維持し、自動で開いたままのページを強制更新しない。更新履歴では状態のみを表示し、手動確認・即時適用ボタンは設けない。「次回起動で反映予定」と表示された場合は、PWAを完全に終了し、同じサイトのほかの画面も閉じてから開き直す。旧版を使用する画面がすべて閉じると待機版が有効化される。
ブラウザタブとPWAが保存領域を共有する環境では、同じService Workerの旧版を使用するタブも閉じる必要がある。
広告・問い合わせフォーム等の外部通信はオフラインでは利用できない。

## ローカル自動検証

```sh
npm run build
npm run typecheck
npm run lint
npm run test:worker
npx playwright test
```

Playwrightは `scripts/preview-pwa.mjs` を利用する。Astroの通常の静的previewではWorkerのmanifestルートが再現されないため、手動確認にも `node scripts/preview-pwa.mjs` を使う。
本番とステージングでは `workers/frontend.mjs` がこのルートを処理する。
旧URL `/split/ticket` の301転送はCloudflareの設定で行い、Astroのページとしては生成しない。検証用サーバーでも同じ転送を再現し、旧URLがPWAの保存対象に混入しないことを確認する。
保存容量とSHA-256一覧はビルド時生成の `dist/pwa-assets.json` で確認する。
差分取得は `tests/browser/pwa-update.spec.ts` で検証する。HTMLだけを変更した最終配信データでフォント・WASMのURLと内容が同一であることを確認し、Service Workerスクリプトの更新確認と資材取得を別々に計数する。変更したHTMLだけが取得され、フォント・WASMの取得がゼロであること、再起動後に新版をオフライン利用できることを確認する。
本番採用前にはiPhone・Androidのステージングでも、同条件での差分取得と再起動を確認する。

## 公開前の実機確認（ユーザー担当）

mainへマージする前にステージングで確認する。本番公開済みとは扱わない。

記録: iPhone/Androidの機種、OS、Safari/Chromeの版、確認日、ステージングのcommit。

1. ステージングの乗車券・定期券・IC定期券、経路入力の各画面で条件を設定する。
2. ページ遷移・条件変更後にホーム画面へ追加し、追加時のページと条件で新しく起動できることを確認する。
3. 最初は通信できる状態で起動する。開発者ツールのApplicationでService Workerがactivatedになり、Cache Storageに `kippu-pwa-<version>` が保存されていることを確認する。更新履歴でも「保存済み」を確認する。
4. アプリを閉じてから機内モードで開く。一度も表示していない解説記事・駅名を表示する。
5. 乗車券・定期券・IC定期券の自動検索、乗車券・定期券の経路入力検索・運賃計算を行う。期間・分割禁止駅・分割数を変える。
6. 経路入力検索は既存の進捗バーが更新され、完了時に消えることを確認する。自動検索に追加表示がないことを確認する。
7. 近距離・長距離で計算時間、クラッシュ・停止の有無を記録する。再検索・別ページへの移動で古い結果が混ざらないことを確認する。
8. 通信を戻し、別版をステージングに配信する。旧画面で入力・計算を続けても画面が強制更新されないことを確認する。
9. 新版のService Workerがwaitingになり、新版のキャッシュが保存された後、同じサイトのタブとアプリをすべて閉じて再起動する。通知なしで新版が有効になることを開発者ツールで確認する。
10. 新版の保存後も開いている画面は再読み込みされず、手動更新ボタンがないことを確認する。別画面が旧版を使用している間は新版が待機し、PWAと同じサイトの旧画面をすべて閉じて開き直すと新版に切り替わることを、iPhone・Androidのホーム画面PWAで確認する。
11. 同じ画面サイズの通常ブラウザと比較する。日本語フォント・改行・既存の進捗表示が一致し、更新履歴以外にオフラインや更新の案内が追加されていないことを確認する。

両端末の確認完了までmainへ反映しない。古いOSや実機未確認の端末は検証済みとしない。
容量不足・OSの保存領域削除後・初回保存前はオフライン動作を保証しない。

## 緊急復旧

`sw.js` を単に削除しても、既存端末のService Workerは残る。
復旧用配信ではクライアントのService Worker登録を止め、`sw.js` を以下の解除用コードで置き換える。
通常の `build-pwa.mjs` に上書きされないよう、ビルド後に置き換える。最初はステージングで確認する。

```js
self.addEventListener('install', () => self.skipWaiting());
self.addEventListener('activate', event => event.waitUntil((async () => {
  for (const name of await caches.keys()) {
    if (name.startsWith('kippu-pwa-')) await caches.delete(name);
  }
  await self.registration.unregister();
})()));
```

解除用Workerにはfetchハンドラーを置かない。通信できる状態で通常ページが読み込めることを確認する。
既にオフラインの端末へは配信できないため、復旧は通信復帰後となる。
解除用 `sw.js` は既存端末の更新機会を確保するため配信を継続する。

旧版のService Workerは状態応答に未対応の場合がある。その場合は「保存状態を確認できません」と表示する。この状態表示機能自体が未配信の旧画面にはボタンを後付けできないため、初回だけは従来の再起動による切り替えが必要。

- 保存対象: 188ファイル、18,116,037 bytes（約17.28 MiB）。フォントは124ファイル、約4.98 MiB。HTTP圧縮後の実通信量ではない。
- Go全テスト、WASM初期化テスト、型検査、ESLint、golangci-lint、Knip、Workerテスト38件を実行。
- Chromiumのブラウザテスト全87件が成功。旧URLの301転送と保存対象からの除外、Manifest配信、保存後の全券種の計算、説明ページ、フォント、既存進捗、通常検索でのWorker共有、タイムアウト時の端末内計算を含む。
- ビルドは成功。iPhone・Androidの実機確認、画面比較、実機での複数画面・再起動を伴う無通知更新は未完了。ステージングの配信完了は未確認。本番反映は行っていない。
- サーバー側DPベンチマーク（3回、各300ms）の中央値: smallは15.46→16.00μs、largeは876.7→842.2μs。両方2 allocs/op。短時間のローカル測定であり、本番レイテンシの保証ではない。


## 更新履歴の状態表示・手動更新の検証

- Workerテスト43件、関連ブラウザテスト10件で、通常ブラウザの登録抑止、新版保存失敗時の旧版維持と再試行、待機版の手動適用、複数画面時の適用拒否、適用後のオフライン利用を確認する。
- iPhone・Androidでの実機確認と本番配信は別途必要。

- 更新メッセージはevent.originと送信元URLの両方を検証し、異なるオリジン・空文字・nullオリジンを拒否する。検証用サーバーはビルド済み資材のみを配信し、不正なリクエストURLを拒否する。

- エラー詳細は画面のメモリだけで保持し、終了・再読み込みでは消える。更新履歴への遷移時に更新確認を再試行する。資材取得・整合性検証・保存の失敗は対象パスとブラウザが返した理由を表示し、再試行成功後に解除する。
- Workerへの状態問い合わせは10秒で応答なしと表示する。更新履歴を表示中のインストールは15秒ごとに状態だけを再確認する。インストール・資材保存・経路計算自体を時間切れで停止しない。
- Workerの登録失敗、資材のハッシュ不一致、状態取得の無応答、再読み込みによるエラー消去をブラウザテストで検証する。通信エラーだけでリダイレクト拒否などの具体的な原因を断定しない。
